# Solo Empire Cloud Monitor

Cloudflare Worker that monitors your services 24/7 on the **free tier**.

## Features

- Checks every production service (own + hosted client services) every 5 minutes. The list
  lives in `src/targets.ts`; two cron triggers split it into shards (by a hash of the target name,
  so adding or removing a target never moves the others) so each run stays under the
  free plan's 50-subrequest limit.
- The 31 services that use Railway "sleep when idle" are probed once an hour (a 5-minute probe would
  keep them awake and billed all the time), so an outage there is reported within about 2 hours.
  Everything else is probed every 5 minutes.
- Telegram alert when a target fails twice in a row (about 10 minutes), a reminder every 6 hours
  while it stays down, and a recovery message.
- Heartbeats for scheduled jobs: `POST /heartbeat/<job>` with `Authorization: Bearer
  <HEARTBEAT_TOKEN>`. A report with `"ok": false` alerts straight away; a job that misses its window
  (`db-backup`: 26 hours) alerts too.
- `/` (SPEC-002): public status page for customers, Thai first, services grouped by product (Life OS, Finance, CRM, AI, data, platform, websites) with an overall verdict; stale probes show as "no recent data". Linked from SaaS footers.
- `/status`: public JSON limited to own services, without URLs or errors. With
  `Authorization: Bearer <MONITOR_TOKEN>` it returns everything, heartbeats included.
- `/check?shard=0|1` (token-protected) probes one shard right away and reports, read-only: it never writes state or sends alerts.
- Each shard stores only the targets it owns, and `/status` reads every target from its own shard,
  with `stale: true` when the last probe is older than 30 minutes (2.5 hours for sleeping services).
- Each shard also watches the next shard's targets and alerts (`⏰ <name> not probed for …`) when
  one has not been probed within that window: a stopped cron or a target that is never due cannot
  report itself. One reminder every 6 hours, and `✅ <name> is being probed again` when it recovers.
  New targets and a freshly deployed watcher get a full window first.
  If both shard crons stop, nothing in this Worker can report it, so an outside check covers it (next item).
- **Static sweep** (`.github/workflows/static-sweep.yml`, SPEC-003): once a day at 02:23 UTC a GitHub-hosted job checks every live Vercel-only site in `src/static-sites.ts` (generated by the solo-empire coverage registry: `python3 infra/scripts/utils/interface_coverage.py --export-static <this repo>/src/static-sites.ts`), sends one Telegram message listing the sites that are down, and posts heartbeat `static-sweep` (26 h). Run it by hand: `gh workflow run static-sweep.yml`.
- **External watchdog** (`.github/workflows/watchdog.yml`, SPEC-001): a GitHub-hosted job, hourly at :17,
  reads the public `/status` and alerts Telegram directly (`[monitor-watchdog] …`) when the monitor is
  unreachable or no target has been probed for 30 minutes. A failed run is the fallback channel (GitHub
  emails the owner). A healthy run posts heartbeat `monitor-watchdog`, which this Worker watches (6 h),
  so each side reports when the other one stops. Secrets: `HEARTBEAT_TOKEN`, `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_CHAT_ID` (Infisical `/monitoring` and `/telegram` NOTI). It sends one message every hour while
  the problem lasts, with no recovery message. Run it by hand: `gh workflow run watchdog.yml`.
- KV writes are the tightest free-plan limit (1,000 a day for the whole account; measured 1,150 on
  2026-11-11 before this change). A shard state is written when anything alerting depends on changed
  (status, failure count up to the down threshold, alert queue, stale watch), after every hourly probe
  of sleeping services, and otherwise every 10 minutes (about 288 a day
  instead of 576; the cross-shard watch allows 30 minutes). A good heartbeat is rewritten only once its
  record is older than its grace (half its window, at most 1 h), and staleness adds that grace back, so an
  alert still means no report for the full window (it may come up to 1 h later). Failed runs and the first
  good run after a failure always write. Each
  run also reads the other shard's state (one KV read) for seeding and the staleness watch.

## Deploy

The Worker, its KV namespace (`MONITOR_KV`) and its secrets already exist. Credentials come from
Infisical, so nothing depends on a local `wrangler login`:

```bash
source ~/.config/solo-empire/environment.sh
infisical run --projectId "$INFISICAL_PROJECT_ID" --env dev --path /cloudflare --silent -- npx wrangler deploy
```

Worker secrets (`wrangler secret put <NAME>`, value on stdin):

| Secret | Source in Infisical |
|---|---|
| `MONITOR_TOKEN`, `HEARTBEAT_TOKEN` | `/monitoring` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | `/telegram` (`TELEGRAM_NOTI_BOT_TOKEN`, `TELEGRAM_NOTI_CHAT_ID`: the `book_noti_bot` that notifications-dispatcher also uses) |
| `SENTRY_DSN` (optional) | Sentry project in org `personal-yu0`. Unset = Sentry off, the Worker runs exactly as without it. |

`/status` is public but limited to own services. `/check` and the full `/status` need
`Authorization: Bearer <MONITOR_TOKEN>`; `/heartbeat/<job>` needs `HEARTBEAT_TOKEN`.

## Error reporting (Sentry)

`src/sentry.ts` wraps the handler with `@sentry/cloudflare` only when the `SENTRY_DSN` secret is set.
Errors only: no tracing, no trace headers, no breadcrumbs, `dataCollection` all off (the SDK v11 form
of `sendDefaultPii: false`) and an allowlist `beforeSend` scrub that also redacts the Telegram bot
token. The scrub is copied from the shared reference `~/work/b-tier-b/sentry-ref/sentry.ts`; this
repo owns its copy. `compatibility_flags = ["nodejs_als"]` in `wrangler.toml` is needed because the
SDK imports `node:async_hooks`.

## Tests

`npm test` (Vitest, offline: in-memory KV and stubbed fetch) and `npm run typecheck`.
`npx wrangler deploy --dry-run --outdir dist` bundles the Worker without uploading.

## Usage

- **View status page:** `https://monitor.bookchaowalit.com` (the `workers.dev` route is off since 2026-11-04)
- **Get JSON status:** `https://monitor.bookchaowalit.com/status`
- **Manual check:** `curl -H "Authorization: Bearer $MONITOR_TOKEN" https://monitor.bookchaowalit.com/check`

## Cost

**$0/month** on the Workers free plan: about 52 checks every 5 minutes is roughly 15,000 requests
a day (limit 100,000) and roughly 500–600 KV writes a day (limit 1,000): about 288 shard states plus
heartbeats, fewer for jobs that report more often than their grace. Check with the Cloudflare GraphQL `kvOperationsAdaptiveGroups` dataset.

## Known limits (accepted)

- **Public `/status` and KV reads.** Public responses are cached at the edge for 60 s, but cache
  misses are not coalesced, so a flood of uncached requests (an attack) could still use up the
  free plan's 100,000 KV reads a day and make the cron's reads fail until the daily reset. Normal
  traffic is far below this. If it ever happens, add a Cloudflare rate-limiting rule on
  `/status`, or move to Workers Paid.
- **KV is eventually consistent.** A parked heartbeat alert can take up to a minute to appear in
  `list()`. It is picked up on a later run and is never deleted before it has been copied.
